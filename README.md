# LaTeX PDF Review Notes

Source-level LaTeX review notes that become blue revision-text PDF drafts for advisors and reviewers.

`latex-pdf-review-notes` is a lightweight workflow for writing review markers directly in LaTeX source and producing PDF drafts with visible blue revision text and optional PDF comments.

It is designed for manuscript revision workflows where authors need to show changes to advisors, supervisors, collaborators, or reviewers without manually editing the generated PDF.

## What It Produces

- Advisor / supervisor draft: blue revision text plus PDF bubble comments.
- Reviewer-facing marked draft: blue revision text only, without private internal comments.
- Clean LaTeX source: a generated `.tex` file with all review macros removed.

## Daily Use After Personal Installation

1. Open your manuscript folder in VS Code. Keep using the existing root file,
   such as `main.tex`; creating a `main_review_work.tex` copy is optional.
2. For a review manuscript, load `amsmath`, then `advisorreview`, on separate
   preamble lines. Add the supported review macros where needed; optional author
   customization stays in the working source. An ordinary manuscript needs no
   `advisorreview` declaration or author setting.
3. For review exports, choose `latexmk (advisor)` using Build with recipe.
   For ordinary work, the default `latexmk (XeLaTeX)` remains available when configured.
4. If this compile actually used a supported review command, open both named PDFs in
   `.advisorreview/<working-source-stem>/`. The advisor PDF includes any review
   comments; the reviewer PDF omits them. The clean `.tex` snapshot is exported
   there automatically. Otherwise, use the normal PDF at its usual location.
5. Continue editing the original working source and rebuild. Do not edit the
   generated clean snapshot unless you intend to stop automatic replacement.

Preamble setup (keep each declaration on its own line):

```latex
\usepackage{amsmath}
\usepackage{advisorreview}
\renewcommand{\advisorreviewauthor}{Your Name}
```

The author line is optional; the default is `Johnnie`. For example, put
`\pdfrevmark{revised text}{Reason for the revision.}` in the document body.
See [Macro Reference](#macro-reference) for inline math, display math, longer text
and standalone notes. Use the same marked working source for both PDF versions.

No tool files, project task configuration, manual wrapper, or separate cleaning
command is needed for this installed workflow. A document with no executed review
commands receives only its normal build, even if it loads `advisorreview`.
When review commands do execute, the package option `clean` only hides marks in
the normal preview; it does not disable automatic review exports.
The clean PDF is optional and is not generated by the one-click export step.

### One Build, Two Automatic Routes

Use the ordinary `latexmk (XeLaTeX)` recipe for normal compilation and select
`latexmk (advisor)` when review exports are needed. Build runs the selected recipe;
the ordinary latexmk recipe does not perform automatic review exports.

| Selected recipe | No review commands executed (package optional) | Review commands executed with the package loaded |
| --- | --- | --- |
| Original latexmk recipe | Normal PDF only | Normal PDF only, with the source's chosen review mode |
| Installed `latexmk (advisor)` | Normal PDF only | Normal PDF plus named advisor/reviewer PDFs and clean `.tex` |

The installed recipe is a wrapper around latexmk, not a new LaTeX compiler. It
first performs the normal build. The package records whether any of the five
supported review commands actually executed during that compile, and reports
`ADVISORREVIEW-USED:yes` or `no` in the `.log` after the document's last page.
The builder reads this report and uses the `.fls` recorder to identify the loaded
package. Only an executed review command enables the extra exports. `amsmath`
and the optional author setting are **not** switches. The package alone enables formatting/comments;
it does not make the original latexmk recipe export multiple versions or clean
the source.

**Package loaded, but no review commands executed?** Only the normal `main.pdf`
is built; no review export directory is created or refreshed. You can keep the
package and author setup ready for later revisions without redundant exports.
Comments, verbatim examples, uncalled macro definitions and unexecuted branches
do not trigger exports. Using a review command in `clean`/`reviewer` mode, or
using a mark with an empty explanation, still counts: the decision is not based
on visible colors or the number of PDF comments. This records TeX execution,
not proof that marked content is visible in the final page.

**Review commands used, but package not loaded?** The compile fails. For a
recognized undefined review command, the installed builder adds a message naming
that command and asking you to add `\usepackage{advisorreview}` in the preamble;
the original LaTeX error remains available. It does not silently suppress the
error or publish review exports from an old PDF. Other undefined commands keep
their original errors. A syntax error or stale auxiliary file may fail earlier
than the missing command. For example, after removing `pdfcomment` indirectly,
an old `.aux` can contain undefined `\ulp@afterend`. Resolve that first error;
do not mislabel it as an executed review command. The builder does not delete
auxiliary files or exports automatically.

**All review commands removed after an earlier export?** The normal PDF updates,
but existing advisor/reviewer PDFs, clean source, manifest and cache are retained
unchanged. They belong to the last review export, not the current normal build.
The console explicitly says no exports were refreshed; nothing is auto-deleted.

If a local old `.sty` cannot produce the usage report, the builder stops and
shows its loaded path, asking you to update/reinstall instead of guessing the
route. Update both the macro package and installed build script together.

## Requirements

LaTeX kernel 2020-10-01 or newer is required for the end-document usage hook
(the local TeX Live 2021 runtime is supported).

LaTeX packages:

- `pdfcomment`
- `hyperref`
- `xcolor`
- `amsmath` for `equation*`, `align`, and related math environments

For layout-preserving math color, the tool uses LaTeX's `\mathcolor` (or the
locally available `mathcolor.ltx`). If neither is available, a warning is issued
and a limited color fallback is used: keep all subscripts, superscripts, primes,
and operator limits inside the marked argument. No packages are downloaded.

Runtime for clean-source export:

- Python 3.10+ for the installed one-click workflow; no Python libraries need to
  be installed separately for normal use.
- The portable/manual Windows cleaner can use `clean_advisor_review.cmd`.
  The installed one-click workflow does not use that launcher.

PDF reader:

- Acrobat Reader or SumatraPDF is recommended for viewing PDF bubble comments.
- Browser PDF viewers may show the blue revision text but not all comment details.

## One-Time Setup For Local VS Code Use

This installer targets **Windows desktop VS Code with LaTeX Workshop**, using
standard user settings and an existing TeX Live installation. For Overleaf or a
machine without this personal installation, use the separate
[portable workflow](#portable-project-workflow). Git is not required to install.

### 1. Download And Extract

Download the ZIP from [the GitHub repository](https://github.com/JohnneyLee/latex-pdf-review-notes)
using **Code > Download ZIP**, then extract it completely. Do not run the
installer from inside the ZIP. Open the extracted folder in Windows Terminal /
PowerShell; it must contain `install_advisor_review.py`, `advisorreview.sty`,
both runtime `.py` files, and the `integration` folder. Keep that folder together
until setup succeeds; do not copy only the installer into your manuscript.

All command blocks labeled `powershell` below are for **PowerShell**, not CMD,
the Python prompt, or the LaTeX source editor. Do not copy the `PS C:\...>` prompt.
Run installation/update commands from the extracted tool folder, not the paper
folder. For example, after replacing this illustrative path with your real one:

```powershell
Set-Location "C:\path\to\latex-pdf-review-notes-main"
Test-Path .\install_advisor_review.py
```

`Test-Path` must return `True` before proceeding.

### 2. Check Existing Dependencies

You need Python 3.10+, Node.js, TeX Live with latexmk and the packages listed
above, desktop VS Code, and its LaTeX Workshop extension. Run these checks one
line at a time:

```powershell
python --version
node --version
code --version
code --list-extensions | Select-String "latex-workshop"
latexmk -v
kpsewhich -var-value=TEXMFHOME
kpsewhich pdfcomment.sty
kpsewhich hyperref.sty
kpsewhich xcolor.sty
kpsewhich amsmath.sty
```

Confirm Python is at least 3.10, LaTeX Workshop is listed, latexmk actually runs,
and each `kpsewhich` lookup prints a path. Stop if a command fails or a required
package is missing; resolve the specific dependency before continuing. The
installer downloads nothing and does not install Python, Node.js, extensions or
LaTeX packages, change PATH, or elevate privileges. A full regression-test
environment (Pillow/pypdf and PDF command-line tools) is not needed for normal use.

If `python` is not recognized or resolves to the wrong program, do not assume
`py` is available. Locate your real `python.exe`, replace the example path below,
and use PowerShell's `&` to invoke it. Never reuse another person's Python path:

```powershell
$Python = "C:\path\to\python.exe"
& $Python --version
& $Python .\install_advisor_review.py --dry-run
& $Python .\install_advisor_review.py
```

Use either this explicit-interpreter route or the normal route below, not both.
The installer remembers the interpreter used, so daily builds do not depend on
the `python` alias. If `node`, `code`, `latexmk`, or `kpsewhich` is missing from
the terminal, fix that command's availability separately.

### 3. Preview And Install

When `python` works, run these from the extracted tool folder:

```powershell
python .\install_advisor_review.py --dry-run
python .\install_advisor_review.py
```

Run the first command, inspect the printed paths and `Preserved compiler`, and
only then run the second. `--dry-run` changes no files. With no configured user
build tools, the default engine is pdfLaTeX; unsupported existing compiler chains
may stop setup rather than fall back. Do not assume every installation selects
XeLaTeX. A failed preview is a stop condition, not a reason to force installation.
Success ends with `Installed and verified.`; an error message is not success.

The installer copies `advisorreview.sty` into the personal `TEXMFHOME/tex/latex/`
tree and the two runtime scripts into `%LOCALAPPDATA%\latex-pdf-review-notes`.
It then adds one user-level LaTeX Workshop recipe named
`latexmk (advisor)`. When `latexmk (XeLaTeX)` already exists, it remains the
user-level default; otherwise a pre-existing non-review default is retained when
available. If there is no normal recipe, the review recipe is the fallback. It
infers the existing standard pdfLaTeX/XeLaTeX/LuaLaTeX engine, preserves other
recipes/settings and JSONC comments, and backs up existing files before changing
them. It uses VS Code's already bundled TypeScript parser for JSONC edits.
PATH, system-wide TeX configuration, existing tasks, and auto-build/auto-clean
settings are not changed. No watcher, save hook, scheduled job, shell-escape
option, or extra extension is installed.

### 4. Reload And Check The Installation

In VS Code, open the Command Palette with `Ctrl+Shift+P` and run
`Developer: Reload Window`. Then use `LaTeX Workshop: Build with recipe` and
select `latexmk (advisor)` for a review build. Project settings may override
the user-level default.

In PowerShell, these checks should both return `True`:

```powershell
Test-Path "$env:LOCALAPPDATA\latex-pdf-review-notes\build_advisor_review.py"
Test-Path "$env:LOCALAPPDATA\latex-pdf-review-notes\clean_advisor_review.py"
```

From your manuscript folder (outside the downloaded tool folder), also run
`kpsewhich --all advisorreview.sty` to check the personal package is discoverable.
This checks installation, not that a manuscript compiles; validate the first
real Build and the three named outputs below before relying on the workflow.

In a manuscript, load `amsmath` before `advisorreview`
as usual, insert the existing review macros, and use the ordinary Build action.
No copying tool files, per-project task file, or manual advisor/reviewer wrapper
is needed with this workflow. **After a successful installation, moving or deleting
the downloaded repository does not affect builds.** The installed recipe calls
the personal script copy, not the download. The `.cmd` launcher is not used.

```text
%LOCALAPPDATA%\latex-pdf-review-notes\
  build_advisor_review.py                   Installed one-click build entry
  clean_advisor_review.py                   Imported by the build entry
  installation.json                        Installation paths and backup names
```

Keep this installed directory, the personal macro package, Python, and TeX tools
in place. This is a personal installation, not a self-contained executable.
Node.js and the downloaded integration script are used only during setup/updates,
not during daily builds. Advanced installations can set `--runtime-home <directory>`;
that installed directory must then remain available.

For a working file named `main_review_work.tex` that actually executes review
commands, one successful Build produces:

```text
main_review_work.pdf                         Normal PDF at the editor's usual output location
.advisorreview/main_review_work/
  main_advisor.pdf                          Blue revisions + private comments
  main_reviewer.pdf                         Blue revisions, no private comments
  main_clean_source.tex                     Source with supported review code removed
  manifest.json                             Source/export hashes and output paths
  build/                                    Generated wrappers and compiler cache
```

Both marked PDFs are generated every time the review workflow succeeds; there
is no default that generates only the advisor PDF. The normal preview follows
the package option in the source (`advisor` is the package default). The builder
reuses that compile for the matching mode and compiles the other mode separately.
It exports clean source only after both PDFs compile successfully, and does not
automatically compile an additional clean PDF.

**Ordinary documents are unaffected by review export:** when no review commands
execute, the tool finishes after the normal build and creates no new
`.advisorreview` outputs, whether the package was loaded or not. Merely mentioning
a command in a comment does not enable exports. Previously generated artifacts
are retained unchanged when the last review command is removed or the package
is later removed; the tool does not delete them.

An unchanged generated clean source is refreshed on the next successful review
export, not by normal-only builds.
If that export was edited manually, or its ownership manifest is missing, the
builder refuses to overwrite it. Keep manual revisions in the working source;
move a finalized export out of the generated directory when archiving it.

The automatic cleaner retains its **single-file review source** boundary. Plain
included TeX, graphics, and bibliography files may remain in the original
project. If a separately included TeX file contains review setup or markers,
automatic clean export stops with an explicit error instead of leaving those
markers in an allegedly clean source. Existing thin advisor/reviewer wrappers
should not be passed to this workflow; build the working manuscript root itself.
An exported source that refers to original assets/inputs should be compiled
with the original manuscript directory as the working directory. The generated
clean file is a snapshot, not a self-contained submission bundle or proof of
advisor acceptance.

For a terminal build without VS Code:

```powershell
python "$env:LOCALAPPDATA\latex-pdf-review-notes\build_advisor_review.py" .\main_review_work.tex --engine xelatex
```

Compiler mode is explicit in this command. The installed recipe uses the engine
detected during setup; if a project needs a different engine or custom build
steps, keep using its existing recipe or configure an appropriate project recipe.
Workspace-level settings can override user settings. Select `latexmk (advisor)`
explicitly for review exports when a project uses another default.

## Updating An Installed Copy

1. Download and extract the new GitHub ZIP into a **new folder**, keeping any
   local modifications in the old download. Downloading alone does not update the
   installed scripts. There is no automatic updater.
2. Open PowerShell in that new folder. Confirm `Test-Path .\install_advisor_review.py`
   returns `True`, then preview and install with the same two commands:

```powershell
python .\install_advisor_review.py --dry-run
python .\install_advisor_review.py
```

3. Stop on preview/install errors. After `Installed and verified.`, reload VS Code,
   build an existing marked working manuscript, and verify both named PDFs and
   the clean source. Do not edit your manuscript or recreate wrapper files just
   to update the tool.
4. The installer synchronizes the personal `.sty` **and** both runtime scripts,
   preserving the detected engine and unrelated settings. Existing changed files
   receive timestamped backups; unchanged payloads do not duplicate recipes or
   backups. Installed copies do not follow edits made in a download automatically.

If you used an explicit Python path, use the same `& $Python ...` installation
commands instead, redefining `$Python` in a new PowerShell session. If Python
itself moved, invoke the installer with its new executable so the recipe is
updated. Use the same `--runtime-home` on updates if you chose a custom directory.
Merely moving or deleting the downloaded folder needs no reinstall. Do not move
or delete the personal installed runtime directory.

For an installation that deliberately uses a custom directory (for example,
personal TeX scripts to avoid redirected AppData), run updates with the same
directory rather than reverting to the default. From the new download:

```powershell
python .\install_advisor_review.py --runtime-home "$env:USERPROFILE\texmf\scripts\advisorreview" --dry-run
python .\install_advisor_review.py --runtime-home "$env:USERPROFILE\texmf\scripts\advisorreview"
```

This is an alternative, not an extra step for default installations. Check the
existing `advisor-review-build` tool path in VS Code settings or the installed
`installation.json` to see which directory your installation actually uses.

A project-local copy can still take precedence over the personal installation.
Installation paths and backup names are recorded in the installed
`installation.json` and mirrored in the download's `.advisorreview/installation.json`.
Existing changed runtime scripts and settings are backed up before replacement;
unchanged files do not create additional backups or duplicate recipes. This record
describes installation, unlike a manuscript export's `manifest.json`.

### Removing An Inactive Previous Installation

An old runtime copy is not required after migration has succeeded. To reclaim
space, first reload VS Code, verify one Build, and check the actual
`advisor-review-build` script path in user **and project** settings. Only then
remove the previous runtime directory if nothing still points to it.

The removable directory contains the old `build_advisor_review.py`,
`clean_advisor_review.py`, `installation.json`, bytecode cache and any backups
inside that old directory. Do not remove the active runtime, the installed
`advisorreview.sty`, the whole `TEXMFHOME`/AppData directory, a manuscript folder,
or `.advisorreview` PDF/source exports. If unexpected files or directory links
are present, inspect them before deleting anything. Do not delete a path just
because it resembles an example in this README.

This is optional, explicit cleanup, not an automatic installer action. Moving
the download needs no reinstall; moving the **active installed runtime** still
requires updating the recipe. Retaining old installations for comparison is
not necessary for normal use.

## Portable Project Workflow

The original project-local workflow below remains supported for collaboration,
Overleaf, and machines where the personal package has not been installed.

Copy these files into the same folder as your manuscript:

```text
advisorreview.sty
clean_advisor_review.py
clean_advisor_review.cmd
```

Create a review working copy of your manuscript:

```powershell
Copy-Item .\main.tex .\main_review_work.tex
```

In `main_review_work.tex`, load the package:

```latex
\usepackage{amsmath}
\usepackage{advisorreview}
```

Optionally set the PDF comment author:

```latex
\renewcommand{\advisorreviewauthor}{Johnnie}
```

Add review notes in the body:

```latex
\pdfrevmark{revised text}{Explain why this text changed.}
\pdfrevmath{$\alpha_k>0$}{Explain the notation change.}
```

Create an advisor wrapper:

```latex
% !TEX root = main_advisor.tex
\PassOptionsToPackage{advisor}{advisorreview}
\input{main_review_work.tex}
```

Create a reviewer wrapper:

```latex
% !TEX root = main_reviewer.tex
\PassOptionsToPackage{reviewer}{advisorreview}
\input{main_review_work.tex}
```

Compile:

```powershell
latexmk -pdf -interaction=nonstopmode -halt-on-error main_advisor.tex
latexmk -pdf -interaction=nonstopmode -halt-on-error main_reviewer.tex
```

Generate a clean source after the review draft is accepted:

```powershell
.\clean_advisor_review.cmd .\main_review_work.tex .\main_clean_source.tex --force
```

Verify that the clean source has no review macros:

```powershell
Select-String -Path .\main_clean_source.tex -Pattern "advisorreview|pdfrev|printpdfreviewlist"
```

No output means the clean source passed this check.

## Macro Reference

### PDF note at the current position

```latex
\pdfrevnote{comment}
```

- Advisor mode: PDF bubble comment.
- Reviewer mode: hidden.
- Clean source export: removed.

### Mark short text in blue

```latex
\pdfrevmark{text}{comment}
```

- Advisor mode: blue text plus PDF comment.
- Reviewer mode: blue text only.
- Clean source export: keeps `text`.

### Mark inline math in blue

```latex
\pdfrevmath{$\alpha_k>0$}{comment}
```

Keep the full `$...$` in the first argument. This makes clean-source export straightforward.

### Mark display math content in blue

```latex
\[
  \pdfrevformula{\dot V(t)\leq -\alpha\|x(t)\|^2+\eta\|e(t)\|^2}{comment}
\]
```

Use inside display math environments such as `\[...\]` or `equation*`.

Mark complete mathematical fragments. Keep each `\left...\right` pair within
the same argument, or keep both delimiters outside it. Ordinary relations,
binary operators, fractions, and script styles retain their normal TeX spacing.
With `\mathcolor` available, scripts outside the marked argument also retain
their normal attachment and placement.

### Mark a sentence or short paragraph in blue

```latex
\pdfrevblock{%
This revised sentence explains the model assumption more precisely.
}{comment}
```

Do not put blank lines inside the first argument. Split multiple paragraphs into multiple `\pdfrevblock` calls.

`\pdfrevblock{paragraph}{comment}` marks a sentence or short paragraph as blue text. It no longer places the text inside a blue background box.

Keep theorem-like environments outside `\pdfrevblock`, and mark their content.
This leaves theorem headings, numbering, and structure under the document
class's control. Older releases of the macro inserted paragraph breaks and
vertical space; the current release no longer inserts either.

```latex
% Not recommended
\pdfrevblock{%
\begin{theorem}
The revised theorem statement.
\end{theorem}
}{comment}
```

Mark only the content inside the theorem-like environment:

```latex
% Recommended
\begin{theorem}
\pdfrevblock{The revised theorem statement.}{comment}
\end{theorem}
```

The same rule applies to `theorem`, `lemma`, `proposition`, `corollary`, and similar environments. For a short phrase inside those environments, `\pdfrevmark{text}{comment}` is also suitable. Both macros now preserve the surrounding paragraph layout. Add paragraph breaks explicitly in the manuscript when they are intended.

## Layout And Spacing

Review marks should change color and comment metadata, not the manuscript's
layout. The 2026-10-26 fix removes the old math wrapper that changed relation
spacing and operator limits. PDF comments use native, zero-size annotation nodes
in pdfLaTeX, XeLaTeX, and LuaLaTeX, rather than inserting boxes between symbols.
These remain ordinary clickable PDF text comments. Their icon rectangles are
offset above the anchor without reserving space; the reader controls how icons
look, and nearby icons can overlap in heavily annotated formulas.

The color remains `RGB (0, 0, 255)`: this is blue revision text, not a background
highlight. This update does not change the existing source syntax or the two
advisor/reviewer modes. Replace the project's local `advisorreview.sty` with the
updated file and rebuild both PDF roots. A different local copy can take
precedence over a personal/global installation; check the loaded path in the
LaTeX log if the old spacing persists.

For a visual comparison, compile `examples/spacing_comparison.tex` using the
same example build workflow below. It shows unmarked, previous, and fixed math.

## Clean Source Export

The package option `clean` can hide marks visually, but it does not remove review macros from the source.

In the installed one-click workflow, clean source is already exported after
both marked PDF builds succeed. No additional clean command is needed. After
review is accepted, archive the accepted snapshot separately while retaining
the marked working source. If assets/inputs are referenced relatively, retain
them and use the original project directory when compiling the exported source.
The cleaner does not rewrite ordinary `% !TEX root` comments; if an archived
clean file is used as a new editor root, update any such comment that still
points to the marked source.

For the portable/manual workflow, or an explicit standalone export, use:

```powershell
.\clean_advisor_review.cmd .\main_review_work.tex .\main_clean_source.tex --force
```

The cleanup script removes:

- `\usepackage{advisorreview}`
- `\renewcommand{\advisorreviewauthor}{...}`
- `\pdfrevnote`
- `\pdfrevmark`
- `\pdfrevmath`
- `\pdfrevformula`
- `\pdfrevblock`
- `\printpdfreviewlist`

It uses balanced-brace parsing for the supported review macros. Retained first
arguments are cleaned recursively, so supported review macros may be nested
without leaking review code into the clean export. Adjacent marks are still
preferred when separate note ownership is clearer. The cleaner is not a full
TeX parser.

## Known Limitations

- PDF comment display depends on the PDF reader.
- `\pdfrevmark` is for short text, not arbitrary paragraphs.
- `\pdfrevformula` should be used inside math environments.
- Keep matching math delimiters together; do not split a `\left...\right` pair across a review macro's argument boundary.
- On older LaTeX installations without `\mathcolor` or `mathcolor.ltx`, include complete scripts and operator limits in the first argument; the fallback does not support external script attachment.
- The zero-size annotation path is for direct PDF output with pdfLaTeX, XeLaTeX, or LuaLaTeX. DVI/PostScript workflows are outside the tested target.
- The optional PDF comment list uses author/subject entries; custom `pdfcomment` list styles and global annotation appearance settings are not mirrored by the native annotation path.
- The cleanup script handles the supported macros but may fail on unusual TeX category code tricks or verbatim-like content inside macro arguments.

## Regression Tests

With local `pdflatex`, `pdftoppm`, `pdftotext`, Python 3, Pillow, and pypdf available, run from
the repository root:

```powershell
python -m unittest discover -s tests -v
```

The build integration tests also use local `latexmk`/BibTeX. Installer tests use
an existing VS Code installation and Node.js (and skip when unavailable); they
write only project-owned test settings, not your actual VS Code settings.

The tests compile an unmarked reference plus advisor, reviewer, and clean
variants. They hide annotation icons and normalize blue text to black. With
pdfLaTeX, marked PDFs must match clean-mode glyph pixels exactly. All engines
must preserve the measured TeX box dimensions and keep PDF word coordinates
within 0.05 PDF points of the unmarked source. The small coordinate tolerance
allows PDF output rounding when color divides a text run; it is not permission
to add visible space. They also check comment counts, revision colors, custom
authors, Unicode comment contents, and compilation without `mathcolor.ltx`.
This checks the supplied cases, not all
possible document classes or macro combinations. Generated PDFs and images stay
in `tests/_build/<engine>/` and are ignored by Git.

To test another installed compiler without changing any global settings:

```powershell
$env:LATEX_ENGINE = 'xelatex'  # or lualatex
python -m unittest discover -s tests -v
Remove-Item Env:LATEX_ENGINE
```

### 1. 首次下载与安装（每台电脑一次）

本节是 Windows 桌面版 VS Code + LaTeX Workshop 的推荐流程，不要求安装 Git。
Overleaf、WSL、远程环境或其他编辑器请采用 Portable Project Workflow，不能直接
沿用这套本机用户配置。

**第一步：下载并完整解压。** 打开
[GitHub 仓库](https://github.com/JohnneyLee/latex-pdf-review-notes)，选择
Code > Download ZIP。把 ZIP 完整解压，进入能看到 `install_advisor_review.py`
的文件夹；不要在压缩包里直接运行，也不要只复制安装器到论文目录。
安装期间需要同目录的宏包、两个运行脚本以及 `integration` 子目录。

下面的终端命令全部在 **PowerShell** 执行，不是在 CMD、Python 交互窗口或
`.tex` 编辑区执行。不要把终端提示符 `PS C:\...>` 一并复制。
在解压目录中打开 PowerShell，或将示例路径替换为自己实际的解压路径：

```powershell
Set-Location "C:\path\to\latex-pdf-review-notes-main"
Test-Path .\install_advisor_review.py
```

第二行必须返回 `True`。若为 `False`，先找到正确目录，不要继续安装。

**第二步：检查已有环境。** 需要 Python 3.10+、Node.js、TeX Live/latexmk、
桌面版 VS Code，以及其中的 LaTeX Workshop 扩展。逐行执行：

```powershell
python --version
node --version
code --version
code --list-extensions | Select-String "latex-workshop"
latexmk -v
kpsewhich -var-value=TEXMFHOME
kpsewhich pdfcomment.sty
kpsewhich hyperref.sty
kpsewhich xcolor.sty
kpsewhich amsmath.sty
```

Python 版本应不低于 3.10；扩展检查应有 LaTeX Workshop；latexmk 应能运行；
各项宏包查询应输出路径。任何命令失败或必需宏包查不到，先停下来补齐对应环境。
工具不会替你安装这些依赖、联网安装宏包、修改 PATH 或提升权限。
普通使用不需要安装 pypdf、Pillow 等开发测试依赖。

**第三步：先预览，再安装。** 仍在工具解压目录，先执行第一行，检查输出的
个人目录、VS Code 设置位置与 `Preserved compiler`，确认没有错误后再执行第二行：

```powershell
python .\install_advisor_review.py --dry-run
python .\install_advisor_review.py
```

`--dry-run` 不修改文件；最后出现 `Installed and verified.` 才表示安装器完成。
安装器会沿用能识别的用户编译配置；未配置用户构建工具时默认 pdfLaTeX，不是
固定使用 XeLaTeX。已有编译链不能识别时可能停止安装，并非一律回退默认值。
预览或安装报错时，不要直接跳到编译论文。

如果 `python` 命令不可用、指向错误程序或报告“没有关联的应用程序”，先找到
自己真正的 `python.exe`。将下面的示例路径换成实际路径后，改用这一组命令，
无需照搬作者电脑上的用户名和 Python 安装位置，也不要求必须有 `py` 命令：

```powershell
$Python = "C:\path\to\python.exe"
& $Python --version
& $Python .\install_advisor_review.py --dry-run
& $Python .\install_advisor_review.py
```

同样先确认版本和预览结果再安装；两种安装写法选一种即可。`&` 是 PowerShell
调用带引号路径的写法。`$Python` 只在当前终端会话中有效，但安装器会把实际
解释器路径保存到 VS Code 配方，之后日常 Build 不需要再设置这个变量。
若缺的是 `node`、`code` 或 TeX 命令，则需另外解决相应命令不可用的问题。

**第四步：刷新并检查。** 在 VS Code 按 `Ctrl+Shift+P`，执行
`Developer: Reload Window`。可在 PowerShell 检查两个运行脚本，正常都返回 `True`：

```powershell
Test-Path "$env:LOCALAPPDATA\latex-pdf-review-notes\build_advisor_review.py"
Test-Path "$env:LOCALAPPDATA\latex-pdf-review-notes\clean_advisor_review.py"
```

再进入自己的论文目录（不要停留在下载目录），执行 `kpsewhich --all advisorreview.sty`，
应能找到个人宏包副本。安装检查成功不等于论文编译成功；继续按第 2、3 节在工作稿
中添加审阅命令并 Build，以实际生成三份产物作为首次使用的完成标准。

个人安装只需执行一次。日常不需要再运行安装器，也不需要向每个论文项目复制
`.sty`、Python 脚本或 `.cmd`。

用 VS Code 打开论文所在的文件夹，在现有论文根文件中使用本工具即可。
例如已有 `MB_LD.tex`，可以直接把它作为工作稿；**不强制复制或重命名为
`MB_LD_review_work.tex`，也不需要手工建立 `MB_LD_advisor.tex` 和
`MB_LD_reviewer.tex`**。是否另存工作稿，由自己的版本管理习惯决定。

安装成功后，编译和清理脚本位于固定的个人工具目录：

```text
%LOCALAPPDATA%\latex-pdf-review-notes\
  build_advisor_review.py
  clean_advisor_review.py
  installation.json
```

`%LOCALAPPDATA%` 表示各使用者自己的本地应用数据目录；在 PowerShell 命令里写为
`$env:LOCALAPPDATA`，不要把 `%LOCALAPPDATA%` 原样当作 PowerShell 变量。VS Code 调用这里的
脚本，不调用下载目录中的脚本或 `clean_advisor_review.cmd`。因此安装成功后，
**移动或删除下载的项目文件夹不会影响一键编译**。不要删除这个已安装目录或
个人宏包目录；Python 和原有 TeX 工具仍然必须保留。日常编译不需要 Node.js。

### 2. 导言区与正文怎么写

在工作稿导言区加载宏包。宏包声明和作者设置各占一行，方便之后清理源码。
`amsmath` 放在 `advisorreview` 前；其他已有论文宏包按项目需要保留。

```latex
\usepackage{amsmath}
\usepackage{advisorreview}
\renewcommand{\advisorreviewauthor}{Your Name}
```

作者设置可省略，默认作者为 `Johnnie`。不同使用者把 `Your Name` 换成自己的
名字；工作稿中保留该设置，导出的干净源码会删除它。

正文按对象选用以下五种命令，说明文字只在导师版中成为 PDF 批注：

```latex
% 独立备注，不改变正文颜色。
\pdfrevnote{已检查后续类似符号，并一并修正。}

% 短文字变蓝，并附带说明。
\pdfrevmark{revised text}{重写了这一短语。}

% 完整行内公式：保留公式自己的数学定界符。
\pdfrevmath{\(\alpha_k>0\)}{补充了正性条件。}

% 行间公式：命令放在数学环境内部，不把环境本身包进去。
\begin{equation*}
  \pdfrevformula{\dot V(t)\leq-\alpha V(t)}{修正了导数估计。}
\end{equation*}

% 整句或短段落变蓝；不自动换段，也不增加上下留白。
\pdfrevblock{This revised sentence explains the assumption.}{澄清了假设的含义。}
```

标记采用纯蓝色文字 `RGB (0, 0, 255)`，不是背景底色。无需填写审稿人编号。
定理、引理、命题环境保持在外面，标记其内部需要修改的文字；完整例子见
Macro Reference。数学片段的 `\left...\right` 必须配对，不要跨越宏参数边界。
不要在 `\pdfrevblock` 的第一个参数中放空白行。

### 3. 日常一键编译，同时得到三份产物

保存工作稿后，使用 LaTeX Workshop 的 Build。安装器添加的审阅配方名为
`latexmk (advisor)`；若已有 `latexmk (XeLaTeX)`，它仍是用户级默认配方。

普通编译使用默认配方；需要导出审阅版本时，选择 `latexmk (advisor)`。
Build 按钮执行当前选择的配方；审阅配方内部仍调用
latexmk，并在正常编译后根据本次是否实际执行了审阅命令自动分流：

| 配方 | 没有执行审阅命令（可以加载宏包） | 加载宏包且实际执行了审阅命令 |
| --- | --- | --- |
| 原来的 latexmk 配方 | 只编译普通 PDF | 仍只编译一份 PDF，批注效果由源码中的宏包选项决定 |
| `latexmk (advisor)` | 只编译普通 PDF，不新建审阅导出 | 保留普通 PDF，另导出导师版、审稿人版 PDF 和干净 `.tex` |

加载宏包负责让批注命令和蓝色文字生效；新增配方负责自动生成多版本与清理源码，
两者不是一回事。安装个人宏包后，原来的 latexmk 配方也能正常编译带标记的论文，
但它不会因此自动获得“多版本导出”功能。

宏包会在上述五个命令实际执行时，记住“本轮使用过”；在文档最后一页处理完成后，
向 `.log` 写入 `ADVISORREVIEW-USED:yes` 或 `no`。构建脚本读取这个结果，再用 `.fls`
确定加载的宏包位置。它不是简单搜索源码，也不是检查 PDF 中有没有气泡。
注释、逐字示例、未执行的条件分支、未调用的自定义命令中的审阅命令都不触发导出。
只标色而说明为空仍算使用，`clean` 或 `reviewer` 模式中执行命令也算使用。
这里记录的是 TeX 执行情况，不保证执行过的内容一定出现在最终可见页面。
`amsmath` 和作者设置都不是启用开关，单纯加载 `advisorreview` 也不是。

如果列表尚未刷新，执行 VS Code 的 `Developer: Reload Window`。
如果当前项目仍在使用旧配方，通过命令面板的
`LaTeX Workshop: Build with recipe` 选择上述配方。项目自己的 `.vscode`
设置可能覆盖用户级默认值，这时应检查当前项目实际选中的配方。

**编译根文件应为工作稿本身。** 如果旧的 `% !TEX root` 注释仍指向手工建立的
导师版/审稿人版包装文件，应先将它改为指向真实工作稿。这个统一入口会自动
在生成目录内管理必要的包装文件，无需用户手动维护。

当确实使用了审阅命令时，Build 会先正常编译，再补齐另一种审阅模式；两份 PDF 都成功后
才导出干净源码。无需来回切换 `advisor`/`reviewer` 选项，无需再运行清理任务。
这里的“三份产物”指**两份审阅 PDF + 一份干净 `.tex`**；普通预览 PDF 另行保留。
若把普通预览也计入，则共有三个具名 PDF 和一个干净源码文件，不会自动生成干净
PDF。内部编译缓存可能还保留 PDF，不属于额外交付版本。

**只加载宏包，但本轮没有执行审阅命令：** 只更新普通预览 PDF，不创建或刷新审阅
导出目录。可以保留宏包与作者设置，以后需要时再加标记，不必为此切换配方。

**用了审阅命令，却没有加载宏包：** 编译失败。统一入口识别到未定义的受支持审阅
命令后，会指出命令名称并提示在导言区添加 `\usepackage{advisorreview}`，同时保留
原始 LaTeX 错误与日志路径；不会把旧 PDF 当作本轮成功结果，也不会静默忽略命令。
普通公式中的其他未定义命令仍显示原始错误，不会一律误报漏载宏包。
若更早就有语法或缓存错误，编译可能尚未执行到审阅命令。例如移除宏包后，旧 `.aux`
可能先报 `\ulp@afterend` 未定义；应先处理日志中的首个错误，不能将它误判成批注命令
漏载。工具不会自动删除辅助文件或已有导出。

**以前生成过审阅稿，现在所有标记都移除了：** 只更新普通 PDF，既有两份审阅 PDF、
干净源码、导出记录和缓存都原样保留。控制台会明确说未创建/刷新审阅导出，
避免把旧稿误当本轮结果。旧文件不会自动删除，即使干净源码被手工修改也不会碰它。
以后再次启用审阅导出时，原有的手改干净源码保护仍生效。

如果旧的 `advisorreview.sty` 无法报告是否用过命令，构建脚本会停止并给出实际加载
路径，提示同时更新宏包与构建脚本。论文目录中的旧宏包可能覆盖个人安装副本，
不要在无法判断使用情况时继续当成普通稿。

原来已经开启的“保存时编译”设置会继续生效，因此保存也可能触发同一流程。
本工具没有新增后台监控或保存钩子。两种 PDF 需要分别排版，单次操作不代表
只执行一次 LaTeX 编译；它会复用已完成的对应模式，并保留编译缓存。

日常最短操作就是：**打开论文文件夹 → 修改并保存工作稿 → 选择需要的配方并 Build**。
使用审阅配方时，未执行审阅命令只生成普通 PDF；实际使用审阅命令才另导出审阅文件。
不要为两份 PDF 来回修改宏包选项，也不需要另外运行清理脚本。
首次用实际含有审阅标记的工作稿检查时，应确认导师版有对应批注、审稿人版无本工具批注、两版修改文字均为蓝色，
并确认原工作稿仍保留审阅命令。

若临时不用 VS Code，可在论文目录运行已安装入口。下面以 XeLaTeX 为例；按论文
实际编译器把 `xelatex` 换成 `pdflatex` 或 `lualatex`，不必改变论文原有编译器：

```powershell
python "$env:LOCALAPPDATA\latex-pdf-review-notes\build_advisor_review.py" .\MB_LD.tex --engine xelatex
```

这是备用命令，不是日常 Build 的额外必做步骤。若当前 `python` 命令不可用，可用
前面设置的 `& $Python` 代替 `python`；VS Code 配方本身已记录安装时的解释器路径。

### 4. 输出在哪里，应该给谁

以实际使用审阅命令的 `MB_LD.tex` 为工作稿，结果位于它所在目录下：

```text
MB_LD.tex                           继续编辑的工作稿，审阅宏保留
MB_LD.pdf                           编辑器正常输出/预览位置，可受 outDir 设置影响
.advisorreview/MB_LD/
  MB_LD_advisor.pdf                 给导师：蓝色修改文字 + 内部批注
  MB_LD_reviewer.pdf                给审稿人：蓝色修改文字，无本工具的内部批注
  MB_LD_clean_source.tex            干净源码：保留正文，删除支持的审阅代码
  manifest.json                     自动导出记录，用于检查文件是否被手工改动
  build/                            自动生成的包装文件及编译缓存
```

如果工作稿命名为 `MB_LD_review_work.tex`，生成目录则是
`.advisorreview/MB_LD_review_work/`，里面的三份文件仍叫
`MB_LD_advisor.pdf`、`MB_LD_reviewer.pdf`、`MB_LD_clean_source.tex`。

普通预览 `MB_LD.pdf` 显示哪种模式，取决于工作稿的宏包选项；不写选项时默认
为导师模式。对外发送时，按上面的明确文件名选择，尤其不要把导师版误发给
审稿人。推荐用 Acrobat Reader 或 SumatraPDF 查看导师批注，阅读器显示能力
有所不同。

后续一直修改原工作稿。成功 Build 且实际使用了审阅命令后，工具会刷新两份 PDF 和未被手工修改的
干净源码。干净源码是当前修改的快照，不意味着导师已经认可；确认后再归档。
若使用 Git，可以在论文项目的 `.gitignore` 中加入 `.advisorreview/`，避免把
编译缓存当成论文源码提交。

### 5. 普通论文和不再需要批注的情况

本轮没有执行审阅命令的论文，只执行正常编译，不会新建或刷新导师版、审稿人版
或干净源码。无论是否加载 `advisorreview.sty` 都适用。仅在注释中写到宏包或命令
不会触发导出；以前生成的文件原样保留，不代表本轮已更新。

`\usepackage[clean]{advisorreview}` 只让普通预览不显示标记；如果仍实际执行了审阅
命令，**不会关闭统一入口的三份导出**。若要回到完全不依赖审阅工具的论文，可以
将已导出的干净源码归档到生成目录之外，再用归档副本继续工作，同时保留原
标记稿以备后续修改。清理器不会自动重写普通 `% !TEX root` 注释；如果归档
副本仍指向旧工作稿，应把根文件指向归档副本本身，避免编辑器又编译旧稿。

不要只注释掉 `\usepackage{advisorreview}` 却留下正文中的 `\pdfrevmark` 等命令，
否则 LaTeX 会报未定义命令。干净源码已处理这些命令，不需要逐条手删。
受支持的审阅命令即使嵌在另一个审阅命令保留的正文参数中，也会被递归清理；
若两条批注分别对应不同文字，仍建议写成相邻标记，以便源码更清楚。
如果其中仍引用原项目的图片、文献或未修改输入文件，应保留这些资源，并从
原论文目录编译它；当前导出不是自动打包的独立投稿项目。

### 6. 工具更新、移动下载目录与恢复

日常改论文不用重新安装，移动或删除下载目录也不用重新安装。此前安装的旧版
仍指向下载目录，需要用新版安装器更新一次，才能获得这个效果。
**下载新版不会自动更新已经安装的副本**，也没有后台自动更新功能。以后更新按以下顺序：

1. 从 GitHub 重新下载 ZIP，解压到一个新文件夹。旧下载目录如有自己的改动，先保留，
   不要直接覆盖它；无需先卸载旧工具，也无需修改论文。
2. 在新解压目录打开 PowerShell，执行 `Test-Path .\install_advisor_review.py`，确认
   返回 `True`。先运行下面第一行预览，确认没有错误后再运行第二行安装：

```powershell
python .\install_advisor_review.py --dry-run
python .\install_advisor_review.py
```

3. 出现 `Installed and verified.` 后，在 VS Code 执行 `Developer: Reload Window`。
   用现有的带标记工作稿 Build 一次，检查导师版、审稿人版和干净源码均更新。
   不用重建两个包装 `.tex`，也不用重新插入审阅宏。
4. 如果使用 Python 完整路径，更新时同样采用 `& $Python ...`，在新 PowerShell 会话
   先重新设置 `$Python`。如果 Python 本身移动了，使用新的解释器重新安装，才能更新
   配方记录的位置。曾用 `--runtime-home` 自选安装目录的，更新时也传入相同目录。

例如，如果为避开应用的 AppData 重定向而使用个人 TeX 脚本目录，**只有已采用
这个自选目录的安装**，才从新下载目录运行下面这组更新命令；默认安装用户仍用前面的
普通命令，不必额外执行：

```powershell
python .\install_advisor_review.py --runtime-home "$env:USERPROFILE\texmf\scripts\advisorreview" --dry-run
python .\install_advisor_review.py --runtime-home "$env:USERPROFILE\texmf\scripts\advisorreview"
```

实际目录以 VS Code 用户设置中 `advisor-review-build` 的脚本路径和已安装的
`installation.json` 为准。使用完整 Python 路径时，仍可用 `& $Python` 替代 `python`。

重新安装会同步个人目录中的宏包和两个运行脚本，并更新构建入口路径。它会在改动已有文件前
保存 `.advisorreview.bak-*` 备份，不会重复添加同名配方。保留这些备份以便恢复
原设置。安装目录中的 `installation.json` 记录本次安装路径及本次备份路径，下载目录
`.advisorreview/installation.json` 也保留一份。即使下载目录不再存在，安装记录仍在。
这与每篇论文导出目录内的 `manifest.json` 不同：后者只用于核对干净源码是否被手改，
不是实时监控或逐次修改历史。

**旧安装可以删除，不需要为对比长期保留。** 先刷新 VS Code、成功 Build 一次，
并确认用户级和项目级配置的 `advisor-review-build` 都不再指向旧路径，再删除确认
停用的旧脚本目录。删除范围仅限该目录内的旧运行脚本、安装记录、字节码缓存和旧备份。
如果其中有其他文件、目录链接，或无法确认是否仍在使用，先检查，不要直接递归删除。

不要删除当前生效的脚本目录、个人安装的 `advisorreview.sty`、整个 `TEXMFHOME` 或
AppData、论文文件夹和 `.advisorreview` 中的 PDF/干净源码。安装器不会自动清理这些
文件；旧安装清理需要单独确认，不应与论文审阅导出混为一谈。

不要移动当前生效的安装目录（默认 `%LOCALAPPDATA%\latex-pdf-review-notes`，自选路径
以配方记录为准）。若误删或移动了
已安装目录，重新下载工具后运行安装器即可恢复。安装不改 PATH，不需要管理员权限，
也不会下载 Python 或 LaTeX 依赖；现有目录权限不足时应停止处理权限问题。

旧论文目录如果还放着自己的 `advisorreview.sty`，可能优先加载旧副本；项目的
`latexmkrc` 也可能另设查找路径。判断实际使用哪份宏包，应检查编译 `.log` 或
`.fls` 中的加载路径，不要仅凭“已完成个人安装”判断。

### 7. 遇到问题先看什么

| 现象 | 检查和处理 |
| --- | --- |
| 只有普通 PDF，没有三份导出 | 若没有实际执行审阅命令，这是正常行为；否则确认选中了新配方、宏包已加载、编译无错误，并检查 `.log` 的 `ADVISORREVIEW-USED` 与输出目录。 |
| 提示审阅命令未定义、宏包未加载 | 在导言区加入 `\usepackage{advisorreview}`；使用数学环境时把 `amsmath` 放在它前面，再重新 Build。 |
| 提示缺少 `usage report` | 加载了旧宏包或旧日志。同步更新安装，检查错误给出的 `.sty` 路径，尤其注意论文目录内的旧副本覆盖个人安装。 |
| 生成了错误论文的 PDF | 检查当前 LaTeX 根文件、旧的 `% !TEX root` 注释以及项目级配方覆盖。 |
| 提示 `Clean export was modified` | 生成的干净源码被手工改动。将手改版本归档到生成目录之外，确认原生成路径不再被占用后重新 Build；工具不会自动删除它，也不要盲目强制覆盖。 |
| 提示 `Unowned clean export` | 该路径已有文件但缺少可验证的导出记录。先检查文件与 `manifest.json`，不要把自己的源码放在自动输出路径中。 |
| 提示 `single-file review sources` | 其他被输入的 `.tex` 文件中还有审阅代码。当前自动清理仅支持审阅代码集中在一个工作稿，不能静默当成已全部清理。 |
| 更换作者后，干净源码无法导出 | 作者设置应单独使用示例中的 `\renewcommand{\advisorreviewauthor}{...}` 一行；旧的自定义审阅设置可能不在清理器支持范围内。 |
| 宏包更新后效果仍旧 | 检查是否加载了项目内旧 `.sty`、是否重新运行安装器，以及 `latexmkrc` 是否优先指向另一份副本。 |
| 移动下载目录后仍提示找不到脚本 | 可能仍是旧版安装配置。用新版安装器更新一次，确认配方指向个人工具目录，而不是下载目录。 |
| Python 或已安装脚本找不到 | 保留 Python 和个人安装目录；若 Python 路径已改变，使用新解释器重新运行安装器。 |

当前个人安装面向本机 Windows 标准 VS Code 用户配置和标准 LaTeX 编译器。
其他电脑、不同 VS Code 配置文件、WSL、远程环境和 Overleaf 需要各自配置；
不能继承本机的安装路径。需要项目随源码一起分发时，使用上面的 Portable
Project Workflow，不必把它与本机的一键流程混用。

排版修复保留了原公式间距、上下标和段落布局；
`examples/spacing_comparison.tex` 提供原始排版、旧版标记和修复版标记对照。
